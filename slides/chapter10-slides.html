10-1 核心哲學

為什麼要換掉 Firebase？Supabase 的三大設計哲學

從專有封閉走向開源標準，徹底擺脫雲端大廠供應商鎖定（Vendor Lock-in）

🔒
傳統 Google Firebase 的痛點
  • 專有 NoSQL 規格：查詢邏輯受限，想做複雜多表 JOIN 幾乎不可能。
  • 嚴重廠商鎖定：資料只能存在 Google 上，未來難以平滑遷移。
  • 擴展費用昂貴：依讀寫次數計費，一旦遇到大數據查詢，費用直線上升。
  • 缺乏原生 AI 向量支援：無法原生支援語意向量索引與相似度比對。
🐘
Supabase 的三大破局哲學
  • 真正的 PostgreSQL：世界上最成熟強大的開源關聯資料庫，支援完整 SQL。
  • 100% 自由遷移：隨時使用 pg_dump 導出備份，隨意搬到 AWS、GCP 或本地。
  • 全端現代開箱即用：建好資料表自動產生 REST/GraphQL API，自帶 WebSocket 即時推播。
  • AI 原生支援：內建 pgvector 擴充，天然就是最強大的企業知識庫後盾！

10-3 AI 向量引擎

AI 時代的必備技能：什麼是 pgvector 向量擴充？

如何讓傳統的關聯資料庫，擁有「理解語意相似度」的超能力？

🧩
啟用與宣告向量欄位

在 Supabase SQL 編輯器中只需一行指令即可開啟：
create extension if not exists vector;

宣告 vector(768) 欄位，即可在每一筆手冊紀錄旁，存放 Google Gemini Embedding 產生的 768 維浮點數陣列。

🎯
語意相似度檢索的本質

當新人提問：「確診可以請假幾天？」
系統將問題轉成 768 維向量，資料庫透過幾何數學計算「兩個向量在高維空間中的距離」，即便文字沒有完全重疊，也能在毫秒內抓出「4.1 傷病假與快篩陽性通報」！

-- 建立包含 768 維向量欄位的手冊資料表
create table handbook_documents (
  id bigserial primary key,
  content text not null,                  -- 手冊原始切塊文字
  metadata jsonb not null,               -- 出處標籤（手冊名、章節標題）
  embedding vector(768) not null        -- 768 維語意特徵向量
);
文字與向量並存於同一資料表中 06 / 14
10-3 向量運算原理

pgvector 3 大距離運算符號與 HNSW 索引加速

數學幾何距離決定最相似段落，多層圖狀索引實現毫秒級海量檢索

最常用 ⭐
餘弦距離 <=>

Cosine Distance
衡量兩向量的方向夾角。值介於 0 到 2 之間，值越小代表語意越相近！

相似度轉換公式：
相似度 = 1 - (A <=> B)

空間幾何
歐式距離 <->

L2 / Euclidean Distance
計算空間兩點之間的直線幾何距離。適合在點座標空間中衡量物理長度差異。

極速運算
負內積 <#>

Negative Inner Product
若輸入的向量已經過正規化（長度為 1），內積計算速度最快，常在超高效能場景使用。

⚡ 向量索引加速：為什麼官方首推 HNSW 索引？

當手冊段落達數萬筆時，逐一比對會變慢。HNSW（分層可導航小世界）建立多層高維導航圖，查詢速度極快且召回率（Recall）極高，一建好後即可動態寫入新資料：
create index on handbook_documents using hnsw (embedding vector_cosine_ops);

餘弦距離是文字語意比對的黃金標準 07 / 14
技術選型深入對決

為什麼選 Supabase 而非 Cloudflare Vectorize 或 Pinecone？

在全端企業知識庫中，純向量庫與全功能關聯資料庫有著本質差異！

評比項目 Supabase (PostgreSQL + pgvector) Cloudflare Vectorize / Pinecone
資料庫本質 全功能關聯式資料庫（PostgreSQL） 純向量索引引擎（Vector Index）
原始長文字儲存 完美支援！Markdown 完整手冊與向量存同表 不支援存長文！只存 ID 與簡短 metadata
查詢步驟 (Roundtrips) 1 趟搞定（查相似度時直接回傳手冊文字） 2 階段查詢（先查出 ID ➔ 再到 D1/KV 撈文章）
混合搜尋 (Hybrid) 原生支援！全文關鍵字檢索 + 向量雙軌融合 僅支援純向量相似度與簡易標籤過濾
可視化除錯後台 內建如 Excel 般的直觀網頁編輯器 主要依賴指令列（CLI）或簡易儀表板
手冊內文與向量一體化存儲，是企業知識庫最穩健架構 08 / 14

10-4 避坑重點 · 致命陷阱 1

⚠️ 致命陷阱 1：連續 7 天無活動自動休眠 (Project Pausing)

專案突然連不上、API 報錯？原來是觸發了官方的伺服器節能休眠機制！

🚨
休眠觸發機制與症狀
  • 規則：免費專案若「連續 7 天完全沒有任何 API 請求或資料庫連線」。
  • 後果：專案狀態自動變更為 Paused 暫停狀態。
  • 症狀：新人打開手冊系統，所有查詢皆回報 Database connection error。
  • 資料安全：放心，資料表與手冊向量完全不會遺失！
⏳
手動恢復有多麻煩？
  • 你必須手動登入 Supabase 網頁後台。
  • 點擊專案旁的 「Restore project」 按鈕。
  • 後端需要 1 ~ 3 分鐘 重新初始化容器與啟動資料庫服務。
  • 如果是主管或客戶臨時上線測試遇到休眠，使用者體驗極差！

⚠️ 另外兩大限制：無自動備份下載 & 500 MB 容量管理

防患於未然！學會純正 PostgreSQL 的備份外掛與檔案分流策略

💾
陷阱 2：免費版沒有「可下載的每日自動備份」

【官方機制】：付費方案享有每日常規自動備份下載與 PITR（時間點還原）；免費方案雖然資料完整，但後台不提供下載 .dump 備份檔的按鈕！

💡 破解秘技：因為它是標準 PostgreSQL，請 AntiGravity 寫一個排程腳本使用 pg_dump，每週自動把手冊內文與資料表結構匯出成 backup.sql 存到本地硬碟或 GitHub 私有庫。

🛑
陷阱 3：500 MB 容量避免被大檔案塞爆

【官方機制】：免費資料庫磁碟上限為 500 MB。

💡 破解秘技：對於 PDF 掃描檔、大圖或影片，絕對不要轉成 Base64 字串直接塞進資料庫欄位！
正確做法是將大檔案上傳到 Cloudflare R2（免流量費） 或 Supabase Storage，資料表內只存放網址 URL，500 MB 足夠存入數百萬字的文章與向量！

10-5 CLI 授權實戰

如何授權 AntiGravity 以 CLI 或腳本操作 Supabase？

自動建表、執行 Migration 遷移、產生 TypeScript 型別與手冊入庫

🔑
途徑一：Supabase CLI (專案管理首選)
  1. 在後台 Account Settings 產生 Access Token (sbp_...)。
  2. 執行 npx supabase login --token 你的Token。
  3. 執行 npx supabase link --project-ref 專案ID 綁定專案。
  4. 超強功能：npx supabase gen types typescript 自動產生全端 100% 精確的 TypeScript 資料表型別！
⚡
途徑二：Service Role Key (手冊入庫最快)
  1. 進入專案「Project Settings」➔「API」。
  2. 複製 Project URL 與 service_role secret。
  3. 寫入專案根目錄 .env：
    SUPABASE_URL=https://xyz.supabase.co
    SUPABASE_SERVICE_ROLE_KEY=eyJh...
  4. AntiGravity 寫入庫腳本 scripts/ingest.js，以最高權限批次將手冊切塊向量寫入資料表！
