5-1 痛點剖析

為什麼靜態網頁需要「後端」？

GitHub Pages 是完美的展示門面，但它無法獨自完成「商業訂單閉環」

❌ 純前端靜態網頁三大天然瓶頸
  • 資料無法保存： 顧客填完表單重整網頁，資料瞬間消失
  • 無法主動發信： 瀏覽器受安全限制，不能自發 Gmail 確認信
  • 傳統後端門檻高： 租 AWS/GCP、維護 SQL，每年花費數千元
🚀 GAS 零成本突破方案
  • 零主機費用： Google 官方免費提供雲端伺服器算力
  • 免安裝任何環境： 打開瀏覽器即可寫程式，零門檻上手
  • 生態系大打通： 試算表當資料庫，Gmail 當自動發信機！

5-2 核心元件

什麼是 Google Apps Script (GAS)？

Google 官方以 JavaScript 為核心的輕量級雲端腳本，天生打通 Google 服務

📊 1. Google 試算表
  • 免建資料庫： 試算表就是現成的視覺化資料庫
  • 即時共編查閱： 手機與電腦隨時查看最新預購名單
✉️ 2. Gmail 電子郵件
  • 官方原生授權： 一行指令即可用個人信箱自動發信
  • 排版精美通知： 自動寄送客製化訂單確認與感謝信
🌐 3. Web App (API 網址)
  • 專屬接收窗口： 生成公開 API 網址接收 POST 請求
  • 跨網域串接： 讓全世界任何靜態網頁都能回傳資料

雖然完全免費，但 Google 為防止濫用設有每日配額（每 24 小時重置）

① 訪客填表送出

訪客在 GitHub Pages 官網填寫預購表單，點擊「確認預購」。

② 前端 fetch() 發送

網頁 JS 將資料打包成 JSON，非同步送往 GAS 的 Web App 網址。

③ doPost() 接收與存檔

GAS 觸發 doPost 解析資料，寫入試算表並發送 Gmail 確認信。

④ 回傳成功並提示

回傳 { status: 'success' }，網頁即時跳出預購成功彈窗！

"Antigravity，我想為『SmartSound Pro 預購網頁』製作 GAS 後端接收腳本。

請幫我寫一段標準 GAS 程式碼：
1. 包含 doPost(e) 接收 5 個欄位：name, email, phone, plan, notes。

🧠 AI 生成程式碼的 4 大關鍵架構
  • doPost(e) 入口： 攔截網頁送來的 POST 資料
  • JSON.parse()： 自動拆解顧客姓名與信箱
  • appendRow()： 一鍵在試算表最底端追加新訂單
  • ContentService： 設定 JSON 輸出解決 CORS！
5-5 避坑法則

Web App 部署兩大「不可犯錯原則」

90% 初學者卡關都在這裡！點選「部署 ➔ 新增部署作業」時請務必核對

👤 原則一：以誰的身分執行（Execute as）
  • 必須選擇： 「我 (Me - 你的 Email)」
  • 關鍵原因： 這樣全世界訪客填表時，才是借用你的權限寫入你的試算表！
  • 錯誤後果： 若選成訪客身分，訪客需先登入 Google 才能提交表單。
🌍 原則二：誰可以存取（Who has access）
  • 必須選擇： 「所有人 (Anyone)」
  • 關鍵原因： 允許任何訪客在未登入狀態下送出預購訂單。
  • 錯誤後果： 若選成「僅限自己」，前端網頁會直接被阻擋報錯！
